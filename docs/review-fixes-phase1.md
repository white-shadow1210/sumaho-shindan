# レビュー改善 第1弾：反映と確認

対象の開始コミット：`49d6055d5e23a925434de130129d2eb2e7fd6277`

## 今回の範囲

1. `diag_latest_tel` による別人の自動紐付けを撤去。未連携・重複は手動確認へ案内。
2. 保存失敗を完了表示しない：GASの確認済み応答 `confirmed:true` を診断・カルテ・予約・アプリチェックで要求。
3. 会員ログインとメニュー選択の順番による割引不具合を修正。
4. 取得失敗のカレンダーを空き枠として表示しない。
5. 長い見積もりJSONを切断せず保存する。
6. 診断の空白氏名・1,000文字超を入力時に確認し、診断・アプリチェックの拡大操作を許可。

年会費は未変更。`prices.html` と `subscribe.html` の年額のどちらを正式採用するかは、Stripeの実際の決済額と照合して決める。

## 変更される利用体験

- 既存LINE IDで顧客が一意に見つかる場合は従来のマイページ表示を維持。
- 未連携や重複時にカルテを自動作成・統合・削除しない。お名前をLINEで知らせてもらい、運営者が本人と対象レコードを確認する。氏名だけで即統合しない。
- 診断完了メッセージだけによるポイント自動付与は停止。既存ポイントは変更しない。
- 回答の保存とLINE連携は別の処理。「即時反映」の断定を削除。
- 単独の `app-check.html` は顧客識別情報を持っていないため、現時点では保存できない旨と担当者への共有方法を表示する。本人紐付けの実装までは、このページを「保存できるフォーム」として新たに案内しない。選択内容は画面に残る。
- 応答を読めない・保存が一部だけ済んだ可能性がある場合は、再送を促さずLINE／Notionで確認する。入力は維持する。

## 本番反映の順序

このPRは実装済みだが、本番への反映を実施した記録ではない。GitHub Pagesと2つのGASは別々に反映される。

1. 現在の本番GASとGitHubの差分を確認する。本番だけの変更がある場合は取り込んでから進め、現在のデプロイ版を記録する。
2. 本体GASに `gas/main.gs`、見積もり保存用の別GASに `gas/mitsumori-save.gs` をそれぞれ反映する。同一GASプロジェクトに両ファイルをまとめて追加しない（doGet/doPost等が重複する）。既存のスクリプトプロパティやURLは保持する。
3. それぞれ既存ウェブアプリのデプロイを新しい版へ更新し、実際のリダイレクト先まで含めてブラウザからJSON応答が読み取れることを、テスト用データで確認する。
4. PRをmainへ反映し、GitHub Pagesの更新を確認する。GASとHTMLの切替は受付が少ない時間帯に近接して実施する。
5. iPhoneのSafari／LINE内ブラウザとiPadで下記を確認する。完了確認後、テスト用の顧客・予約・見積もりを識別して整理する。

新HTML＋旧GASの組合せでは、旧GASが成功を返しても `confirmed:true` がないので「結果を確認できません」になる。これは未確認の完了を防ぐための意図した扱い。逆の旧HTML＋新GASには古い誤完了表示が残るため、切替期間を長くしない。

CORS等で応答が読めない場合に `no-cors` へ戻して完了扱いにしてはいけない。認証・CORSを適切に扱う受信口を整えるまでLINEで受付する。

## 検証

ローカル：`node --test tests/regression.test.cjs`

Node.js標準機能のみ。Google・Notion・LINE通信はすべてモック。テスト結果：21件合格。

- 未連携・重複するLINE IDで、別顧客への書込みがない。
- 一意な既存LINE IDでは従来のマイページ呼出しを維持。
- Notion検索・更新失敗を保存成功としない。検索失敗時に新規顧客を作らない。
- 診断保存、カレンダー保存失敗、顧客不明のアプリチェックの成功／失敗を区別。
- 3,300／5,500／11,000円と無料メニューが選択順に影響されない。
- カレンダーのネットワーク・HTTP・エラーJSON・不正な予定データで空き枠を出さない。
- 長い5人分の見積もりを絵文字を含めて保存・復元できる。上限を超える場合は切断保存せずエラー。
- 予約の失敗JSON・旧形式の成功JSONで完了表示や端末履歴の記録をしない。
- 全HTMLのインラインJavaScriptとGASの構文確認。

## 残る課題・次段階

このPRを「本人認証を完全に修正した」と扱わない。撤去したのは共有電話キャッシュと表示名フォールバックであり、次の経路は別途対応が必要。

- 公開フォームが渡すLINE IDをサーバーで検証すること。電話番号だけで既存顧客に書き込む経路、同じ連絡先を使う家族の扱い。
- 内部カルテ等の更新に対する運営者認証。既存OWNER_KEY保護のある見積もりAPIと区別して対応する。
- LINE Webhookの署名検証ができる受信口。現在の署名なし受理を放置せず、正規通知が途切れない形で移行する。
- 予約を確定する際の排他制御、予定区間の重複検査、再送の重複防止。今回のカレンダー取得失敗対策だけでは二重予約を防げない。
- カレンダー保存後にNotionが失敗した場合は部分保存が残る。自動ロールバック／再送は未実装なので、今回の画面はLINEでの確認へ案内する。確認メールはNotion保存の後に送る。
- 通知メール失敗は予約保存自体を取り消さない。メール配送の到達保証・再試行は次段階。
- 会員資格・価格のサーバー側計算、決済済み状態との連携。今回修正したのはブラウザの割引計算だけ。
- 過去の誤紐付けや途中切断された見積もりの修復は行っていない。根拠を確認して個別に扱う。

この後に、診断の入口を「誰の相談か／買い替え前後・日常の困りごと」から選べる形へ改善する。先に受付の信頼性と本人確認を整える。
